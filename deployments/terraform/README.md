# OpenTAMS — Terraform / OpenTofu deployment (AWS)

> Runs with either **HashiCorp Terraform** (`terraform`, `>= 1.5`) or
> **OpenTofu** (`tofu`, `>= 1.6`). The config is identical for both — every
> `terraform <cmd>` below works as `tofu <cmd>`. This repo is validated with
> OpenTofu (`tofu validate`).

Brings up OpenTAMS and its managed dependencies on an **existing** EKS cluster:

- **RDS Postgres** — the database.
- **S3 bucket** — the media object store.
- **IRSA role** — lets the OpenTAMS pod reach S3 with no static keys.
- **Secret** — `DB_PASSWORD` in a Kubernetes Secret consumed by the OpenTAMS Helm release (see [Secrets](#secrets) for the three ways to manage it).
- **OpenTAMS Helm release** — `../helm/opentams`, wired to all of the above.

[slv]: https://github.com/amagioss/slv
[slv-docs]: https://slv.sh

The cluster itself is **not** created here — you deploy into the cluster you
already reach from your laptop (`kubeconfig`). The Kubernetes side is
cloud-agnostic; only RDS/S3/IAM are AWS.

> **GCP support is planned for a later phase.** The `modules/secrets-slv` and
> `modules/opentams` modules are cloud-neutral by design, so a future `gcp/`
> root (Cloud SQL + GCS + Workload Identity) will reuse them unchanged. Only AWS
> is implemented today.

```
terraform/
├── aws/                 # root module: RDS + S3 + IAM/IRSA + the two modules
├── modules/
│   ├── secrets-slv/     # slv-operator + bootstrap Secret + seal & apply CR
│   └── opentams/        # opentams Helm release
└── gcp/                 # planned (next phase)
```

## Prerequisites

On the machine running `terraform apply` / `tofu apply`:

- `terraform >= 1.5` **or** `tofu >= 1.6`, `aws` CLI (authenticated), `kubectl`, `helm`
- kubeconfig reaching the cluster; AWS creds with RDS/S3/IAM permissions — a
  least-privilege deployer policy is in `aws/iam-deployer-policy.example.json`
  (optional add-on blocks in `aws/iam-deployer-policy.optional.md`)

Additional tools required when using SLV (`use_slv = true`, the default):

- `slv` and `jq` — used by `modules/secrets-slv/seal.sh` to seal `DB_PASSWORD`

OpenTAMS dependencies you must supply (not created here):

- An **external OIDC issuer** (`auth_external_issuer_url` + `auth_external_audience`)
- The cluster's **IAM OIDC provider** — either let Terraform create it
  (`create_oidc_provider = true`) or pass `existing_oidc_provider_arn`

## Secrets

`DB_PASSWORD` (generated by Terraform from `random_password`) must reach the
OpenTAMS pod as a Kubernetes Secret named `var.secret_name` in `var.namespace`.
There are three ways to manage this:

### Install SLV for the first time

No SLV operator on the cluster yet. Terraform installs the
[`amagioss/slv`][slv] operator and seals `DB_PASSWORD` into an SLV CR. The
operator decrypts the CR into a native Secret.

```hcl
use_slv              = true   # default
slv_install_operator = true   # default
slv_env_public_key   = "SLV_EPK_..."
# slv_env_secret_key passed via env:
# export TF_VAR_slv_env_secret_key='SLV_ESK_...'
```

Generate the keys (one-time):

```bash
slv env new service direct --name opentams-k8s --email you@org.com
```

Record `Public Key` → `slv_env_public_key` (safe to commit) and
`Secret Key` → `slv_env_secret_key` (keep secret, never commit):

```bash
export TF_VAR_slv_env_secret_key='SLV_ESK_...'
```

> AWS-native alternative: `slv env new service aws --kms-arn ...` lets the
> operator unwrap its key via KMS (no plaintext key in the cluster).

### Use an existing SLV operator

The operator is running on the cluster under a different team's management. You
only need the EPK to seal secrets against it; you do not install the operator
yourself.

```hcl
use_slv              = true
slv_install_operator = false
slv_env_public_key   = "SLV_EPK_..."  # ask the operator owner for the EPK
# slv_env_secret_key not needed
```

### Manage the Kubernetes Secret yourself

Set `use_slv = false` to skip all SLV resources. You are responsible for
creating the Secret (named `var.secret_name`, default `opentams-secrets`) in
`var.namespace` **before** running `tofu apply`.

```hcl
use_slv = false
```

Create the Secret by any means — for example:

```bash
# Simple kubectl
kubectl create secret generic opentams-secrets -n opentams \
  --from-literal=DB_PASSWORD=<password>
```

Other tools that work with this approach:

- **External Secrets Operator (ESO)** — sync from AWS Secrets Manager, Vault, or GCP Secret Manager into a native Secret
- **AWS Secrets Store CSI driver** — mount secrets from Secrets Manager directly as volume / env
- **Sealed Secrets** (Bitnami) — encrypt-at-rest Kubernetes Secrets committed to git
- **CI/CD pipeline** — inject via `kubectl create secret` as part of your deploy pipeline

## Configure

```bash
cd aws
cp terraform.tfvars.example terraform.tfvars
# edit terraform.tfvars
```

Key inputs: `region`, `eks_cluster_name`, `db_subnet_ids` (same VPC as nodes),
`db_ingress_security_group_ids` (node SG), `bucket_name`,
`auth_external_issuer_url`, `auth_external_audience`, and the secrets scenario
above.

All AWS resources are named `${resource_name_prefix}-${eks_cluster_name}-*`
(default prefix `opentams`) and stamped with `default_tags`
(`{ ManagedBy = "terraform", Project = "opentams" }` by default). The fixed
prefix lets the deployer IAM policy scope to `opentams-*` — if you change it,
update the ARNs in `iam-deployer-policy.example.json` to match.

### Remote state (optional, for teams)

By default state is local (`terraform.tfstate`) — fine for a single operator.
For shared or concurrent use, store state in S3 with locking so two applies
can't clobber each other:

1. Create a dedicated state bucket (not the media bucket), versioning on:
   ```bash
   aws s3api create-bucket --bucket <YOUR_BUCKET> --region <REGION>
   aws s3api put-bucket-versioning --bucket <YOUR_BUCKET> \
     --versioning-configuration Status=Enabled
   ```
2. `cp backend.tf.example backend.tf`
3. Init and migrate the existing local state:
   ```bash
   tofu init -migrate-state \
     -backend-config="bucket=<YOUR_BUCKET>" \
     -backend-config="key=opentams/aws/terraform.tfstate" \
     -backend-config="region=<REGION>"
   ```

`use_lockfile = true` uses S3-native locking — requires OpenTofu >= 1.8 or
Terraform >= 1.10. State holds the DB password, so keep the bucket private and
encrypted (both set above). The deployer needs S3 access to this bucket — see
the "Terraform remote state" block in `iam-deployer-policy.optional.md`.

## Apply

```bash
# Terraform
terraform init && terraform validate && terraform apply

# …or OpenTofu (identical config)
tofu init && tofu validate && tofu apply
```

Order of operations enforced:

1. RDS, S3, IAM/IRSA role, namespace.
2. (Scenario A/B) SLV: operator Helm install + bootstrap Secret, then `seal.sh`
   seals `DB_PASSWORD` into an SLV CR and waits until the operator produces
   `Secret/opentams-secrets`.
3. OpenTAMS Helm release — its pre-install migrate hook reads that Secret and
   connects to RDS.

## How the pieces connect

| Need | Source | Wired by |
|------|--------|----------|
| `DB_PASSWORD` | `random_password` → Secret (via SLV or manually) | `secrets-slv` → `secrets.existingSecret` |
| `DB_HOST/PORT` | RDS endpoint | `module.opentams` `database.*` |
| S3 access | IRSA role on the SA | `serviceAccount.annotations` |
| Bucket/region | S3 bucket | `objectStore.*` |
| JWT validation | your OIDC issuer | `auth.external.*` |

`OBJECT_STORE_ACCESS_KEY_ID/SECRET_ACCESS_KEY` are intentionally absent — the
chart supports omitting them under Workload Identity / IRSA.

## Prometheus / Grafana metrics

Add labels to the OpenTAMS namespace so your Prometheus instance's
`serviceMonitorNamespaceSelector` matches it, and enable the ServiceMonitor in
`extra_values`:

```hcl
namespace_labels = { "monitoring" = "true" }  # kube-prometheus-stack default

extra_values = <<-EOT
  serviceMonitor:
    enabled: true
EOT
```

Check your Prometheus CR to see which labels it selects:

```bash
kubectl get prometheus -A -o jsonpath='{range .items[*]}{.metadata.name}{"\t"}{.spec.serviceMonitorNamespaceSelector}{"\n"}{end}'
```

## Rotating the DB password

`terraform apply -replace=random_password.db` (or `tofu apply -replace=...`)
re-seals the new value (the `data_hash` trigger fires), the operator updates the
Secret, and a Helm upgrade rolls the pods.

When `use_slv = false` you are responsible for updating the Secret and
rolling the pods yourself.

## Destroy

```bash
terraform destroy   # or: tofu destroy
```

`terraform destroy` will refuse to remove the database and a non-empty bucket under the
default settings — that is deliberate. For a dev/demo stack you intend to tear down, set
`db_skip_final_snapshot = true` and `bucket_force_destroy = true`.

## Security

The config is hardened by default: no public RDS access, no public S3, IRSA instead of static
credentials, SSE on S3, TLS-required DB connections. Run `make lint-tf` (wraps `tfsec`,
`trivy config`, and `checkov`) before submitting any Terraform changes.

This module is published, so it defaults to the production-safe value wherever the two
conflict. Turning a default off is a deliberate, cheaper dev choice:

- `db_multi_az` — **defaults to `true`** (Multi-AZ RDS for HA). Set `false` to halve
  instance cost on a throwaway stack.
- `db_skip_final_snapshot` — **defaults to `false`**, which also enables deletion
  protection and takes a final snapshot on destroy. Set `true` only on a stack you
  intend to `terraform destroy`.

Two knobs remain off by default because enabling them is not free or not universally
supported:

- `db_performance_insights = true` — not supported on `db.t3.micro`
- `bucket_kms_key_arn` — customer-managed KMS key for S3 SSE (IRSA role gets `kms:Decrypt/GenerateDataKey` automatically)

RDS IAM database authentication is deliberately not wired up; OpenTAMS authenticates to
Postgres with a password from Secrets Manager. Scanners flag this (`AWS-0176`); the
suppression and its reasoning are in [`.trivyignore.yaml`](../../.trivyignore.yaml).

The `s3:GetObject` policy covers `bucket/*` — this is expected; the app needs object-level
read/write within the single dedicated bucket.

## Notes / limitations

- `seal.sh` runs locally (it needs the `slv` CLI), so applies must run where
  `slv`+`jq` are installed. For CI without `slv`, use Scenario B (existing
  operator with pre-sealed vault committed to git) or Scenario C (manage the
  Secret externally).
- `extra_values` (raw YAML) overrides anything — use it for ingress,
  autoscaling, `serviceMonitor`, `networkPolicy`, or internal-issuer auth.
